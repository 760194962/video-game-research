# 审核（オーディション）列表与出现规则

结论先说：菜单里的审核是**随机刷出来的**。IDOL VISION 属于 c 类栏位里的"20% 替换"，其中 ver4（奖励 7 万粉丝）在一次刷新里的概率约 **1%**。
以下来自对 `default.xex` 的反编译和对审核表的解析，**没有在游戏里实测过概率**。标注"推测"的条目只看过代码或数据、没有验证。

## 1. 数据来源

审核表是 BXR 文件，同一份数据存了两处：

- `root/scene/produce/audition/system/auditionlist.bxr`
- `root/scene/produce/audition/entry.bna` 里的内嵌副本（字段名表更完整）

BXR 是"字符串池 + 节点树"的格式：开头是 `BXR0`，后面是名字偏移表，所有属性值都是字符串（数字也是），由程序在加载时转成整数。
一条审核记录的写法是：先出现 ID 和标题序号，再出现这条记录自己的各项数值。读表时要按这个顺序分组，否则数值会错位到前一条记录上。

字段名（出现顺序）：`category program title place pass fan rank level week chara memories win lose special text texture id network type high low`。

标题文本在同一个文件末尾的 UTF-16BE 表里，记录里的标题序号就是这张表的下标。IDOL VISION ver1~4 对应序号 16~19。

## 2. 审核 ID 与命名规则

ID 前缀是栏位类别，游戏里用格式串拼出来（字符串在 `default.xex` 的 `.rdata`，约 `0x82050DD0`–`0x82050E50`）：

| 格式串 | 例子 |
|---|---|
| `a%d` / `b%d` / `c%d` / `d%d` / `e%d` / `f%d` | 各栏位的固定审核，数字 = 栏位序号（从 1 开始） |
| `b4_%d` | b 类第 4 栏位的变体，共 4 个版本 |
| `c5_%d` | c 类第 5 栏位的变体，共 4 个版本。**这就是 IDOL VISION ver1~4** |
| `d9_%d` / `f9_%d` | d、f 类的偶像限定变体 |

IDOL VISION 的 4 条记录（`fan` 是记录里的数值，含义见第 5 节）：

| 版本 | ID | 标题序号 | fan | rank（高~低） |
|---|---|---|---|---|
| ver1 | `c5_1` | 16 | 25,000 | S ~ D |
| ver2 | `c5_2` | 17 | 30,000 | S ~ D |
| ver3 | `c5_3` | 18 | 50,000 | S ~ D |
| ver4 | `c5_4` | 19 | 70,000 | S ~ D |

四条的 `chara` 都是 `ALL`，`special` 都是空。

## 3. 栏位怎么刷出审核

函数 `0x8230C410`（按栏位类别 `switch`，参数是栏位序号 0~3）负责决定每个栏位放哪条审核。
外层状态机在 `0x82311850`：每个栏位的条目有一个倒计时，到点就调用上面的函数重新刷。倒计时长度由 `0x3C - (int)(rand01 * -60.0)` 得到，约 60~119 秒（推测，常量按反编译读出，没有核对单位）。

随机数函数是 `0x8238CAC8`，返回无符号 32 位整数。游戏里的统一写法是 `(int)(r * 2^-32 * 100.0)`，即 0~99 的均匀整数。

### c 类栏位（case 2，IDOL VISION 在这里）

1. 先看另外三个栏位当前有没有 c5 范围内的审核。有，则这个栏位直接放普通的 `c%d`（数字 = 栏位序号 + 1）。因此 **IDOL VISION 同一时间最多出现一个**。
2. 没有的话掷一次 0~99：结果大于 19（80%）放普通 `c%d`；结果 0~19（20%）放 `c5_%d`。
3. 放 `c5_%d` 时，版本由函数 `0x8230A4F0` 再掷一次 0~99 决定：

| 掷值 | 版本 | 概率 |
|---|---|---|
| 0~29 | ver1 | 30% |
| 30~69 | ver2 | 40% |
| 70~94 | ver3 | 25% |
| 95~99 | ver4 | 5% |

所以 ver4 一次刷新的概率 = 20% × 5% = **1%**（前提是当时没有别的栏位已经是 IDOL VISION）。

### 其他栏位（简述）

- case 0（`a%d`）：按栏位序号固定生成，没有看到随机分支。
- case 1（`b%d` / `b4_%d`）：前三个栏位是普通 `b%d`，第四个栏位用 `b4_%d`，版本同样调用 `0x8230A4F0`，概率和上表一样。
- case 3、4、5：`d%d`/`d9_%d`、`e%d`、`f%d`/`f9_%d`，其中有依据 DLC 是否购买、星期几的分支，没有逐条读完。

## 4. 进入审核时的检查

选中一条审核后，函数 `0x8230A598` 检查能不能进入，不通过就弹提示而不是直接隐藏。对 IDOL VISION 有意义的检查：

- 偶像等级必须落在记录的 `rank` 范围内（`S` 记为 0，`A`~`G` 记为 1~7；ver1~4 是 S~D）。当前等级为 7（G）时跳过这项检查（推测）。
- 周数、`memories`、`win`/`lose` 等字段有对应的范围或最小值检查，ver1~4 的这些字段都是默认值（`memories`=0，`win`=100，`lose`=0），等于不限制。
- `special` 里的标记是用字符串比较解析成位掩码的（`0x8230C410` 后半段）：

| 位 | 标记 | 位 | 标记 |
|---|---|---|---|
| 0x1 | `GET_13STARS` | 0x200 | `SATIATE_JUDGE` |
| 0x2 | `FIXEDSTAR_DANCE` | 0x400 | `GET_15STARS` |
| 0x4 | `FIXEDSTAR_VOCAL` | 0x800 | `ONLY_MEMORIES` |
| 0x8 | `FIXEDSTAR_VISUAL` | 0x1000 | `NO_MEMORIES` |
| 0x10 | `INTEREST_HALF` | 0x2000 | `INSATIATE_JUDGE` |
| 0x20 | `EXAM_ONCE` | 0x4000 | `RANDOM_VOUGUE` |
| 0x40 | `SECRET_JUDGE` | 0x8000 | `ONLY_DUO`（要求 2 人 Unit） |
| 0x80 | `SECRET_RANK` | 0x10000 | `ONLY_TRIO`（要求 3 人 Unit） |
| 0x100 | `HIGHEST_PLUS5` | | |

这些标记名在代码里只负责置位，每个位在别处具体怎么影响判定，除 `ONLY_DUO`/`ONLY_TRIO`（`0x8230A598` 里按 Unit 人数检查）外都没有逐个读。

## 5. `fan` 字段的含义（有把握但未完全证实）

一开始我把 `fan` 当成"出现所需粉丝数"，**这是错的**：

- 代码里没有任何地方拿它和 Unit 的粉丝数比较。
- 它被存进条目结构的 `+0x1628`，之后原样传给审核显示/开场的函数（`0x8230AB70`、`0x822FDE80`）。
- 界面素材里有 `swg_pro_audi_sel_tex_fanup`（"ファンUP"）。
- 数值随版本升高：25,000 / 30,000 / 50,000 / 70,000，符合"越稀有的版本奖励越多"。

所以我判断 7 万是**胜利后获得的粉丝数**。我读到了传参，没有读到最终发奖的代码。

## 6. 复现方法

1. 用 `tools/xex_decrypt.py` 解出 `default.xex`（需要零售密钥，见 [xex-notes.md](xex-notes.md)）。
2. 把镜像按原始二进制导入 Ghidra，基址 `0x82000000`，处理器 `PowerPC:BE:64:64-32addr`（**不要**选带 VLE 或 A2ALT 的变体，指令会错位）。
3. `.text` 从 `0x820E0000` 开始、长 `0x3A9B44`。要手动反汇编这一段再跑分析，直接导入后自动分析几乎不会识别函数。
4. 函数序言 `mfspr r12,LR; bl 0x82451EC4~0x82451EEC` 是寄存器保存的 thunk，Ghidra 会把它们当成"不返回"，导致函数体被截断。要把 `0x82451E00`–`0x82452000` 里的函数都设成可返回，再重建函数。
5. 在 `.rdata` 里搜 `c5_%d`（`0x82050E28`）、`special`（`0x82050DD0`）等字符串，找引用它们的 `lis`/`addi` 对，就能定位到 `0x82308000`–`0x8230D500` 这一带。
