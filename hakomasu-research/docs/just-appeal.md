# 试镜的 Just Appeal（JA）判定

结论先说：**按键时刻离拍点在 ±12% 拍长以内就是 JA，这个窗口是数据表里的固定值，Tension 不参与。** JA 让这一次 Appeal 的基础值 +10（上限 100）。
以下来自对 `default.xex` 的反编译和对 `battle.bna` 的解析，**没有在游戏里实测**。标注"推测"的条目只看过代码或数据、没有验证。

## 1. 节拍函数

`0x820FF778(偏移)` 返回当前播放到第几拍（浮点）：

```
拍数 = (已播放采样数 - 偏移 - 起始偏移[曲]) / (采样率 * 60 / BPM[曲])
```

- 已播放采样数和采样率来自 `0x82431848`。
- `BPM[曲]` 是 float 表，在 `0x824948D8`；`起始偏移[曲]` 是 int 表（单位：采样），在 `0x82494920`。曲号是全局变量 `0x824EE4D0`。
- 还没播到起始偏移时返回一个常量（`0x82004920`）。

声音测试画面（`0x821A93A8`）里的调试显示 `Beat:%c%c%c%c` 和 `OnBeat:%+3d` 用的就是这个函数，后者和下面的 JA 判定是同一套算法。

## 2. 判定算法

普通 Appeal 的处理在 `0x822DE400`（试镜对战状态机里每帧调用的一个状态）。按下 Appeal 键时：

```c
p = (int)(拍数(0) * 100.0) % 100;   // 0~99
if (p > 49) p -= 100;               // 折成 -50~49，0 = 正好在拍点
JA = (-judge <= p && p <= judge);
```

- `judge` 存在试镜数据对象的 `+0x9F4`。全程序只有加载函数 `0x82308008` 写过这个字段（`0x82308074` 的 `stw`），其余都是读取（`0x822DD768`、`0x822DE400`、`0x82306E90`）。**没有任何代码按 Tension 或别的状态修改它。**
- 它的值来自 `root/scene/produce/audition/battle.bna` 内嵌 BXR 里的 `<judge value="12">`（见第 6 节）。
- 因为 `(int)` 截断，`p` 表示拍内小数位于 `[p/100, (p+1)/100)`。所以实际窗口是**拍点前 12% 到拍点后 13% 的拍长**，略偏向后。

## 3. 什么时候能按

- 试镜对战用帧计数器（对象 `+0x18`）驱动，每回合 240 帧，共 9 回合（帧数超过 `0x86E` 就结束）。
- 每回合的第 15 帧打开输入，第 105 帧关闭并结算。也就是每回合只有约 1.5 秒（90 帧）能按。
- 每回合能按的次数 = Unit 人数（`+0xB98`），每按一次减一，同一帧只受理一个键。

## 4. JA 的效果

得分函数 `0x823094E0(数据, Unit, 本回合按键次数, 回合, Appeal 种类, JA, 思い出模式, ...)`：

1. 基础值 = `(能力值[Unit][种类] + 5) / 20`，最少 1。
2. **JA 时基础值 +10。**
3. 普通 Appeal 时，基础值上限 100（思い出ボム那条路径不封顶，另有按评委偏好加倍/减半的计算）。
4. 再按一个计数字段（Unit 区 `+0xD68`，含义未确认）修正：值 0~7 时 −10%，8~15 不变，16 以上 +15%。
5. 本回合按了 2 次就每次 ÷2，按了 3 次就 ÷3。
6. 最后保证评委累计值落在 0~9999。

推论：

- 能力值低时 JA 的 +10 占比很大；能力值让基础值达到 91 以上（能力值 ≥ 1815）后，JA 的加成开始被上限截掉，≥ 1995 时完全没有效果。能力值的单位和游戏里显示的数值是否一致，还没有核对。
- 回合内第一次 JA 时，会按对应评委播放语音（`0x1E`/`0x1F`/`0x20`）和音效。

思い出ボム（`0x822DD768`、`0x822E5E70`）发动时也用同样的方式取一次相位并判断 JA，结果传给三位评委的得分计算。

## 5. 发光的 ○ 和判定时刻（推测）

在 `0x822DE400` 里，○ 的动画进度是用 `拍数(-3200)` 算的，即比判定用的时刻提前 3200 个采样。按 48kHz 算约 67ms，也就是灯会比判定的拍点**早亮**一点。采样率没有核对，反编译里这一处的返回值也被 Ghidra 丢掉了，结论要再确认。

## 6. battle.bna 里的 BXR

`battle.bna` 的 0x2000 处内嵌一份 BXR。这一份的布局（和 [audition.md](audition.md) 描述的是同一种格式）：

| 位置 | 内容 |
|---|---|
| 0x00 | `BXR0`，之后 5 个 u32：元素名数（22）、属性名数（28）、节点数（728）、属性数（1801）、字符串池大小 |
| 0x18 | 名字偏移表：先元素名，后属性名 |
| 之后 | 节点表，每条 28 字节（7 个 s32）：前一节点、后一节点、元素名下标、文本偏移、第一个属性下标、…… |
| 之后 | 属性表，每条 12 字节（3 个 s32）：下一个属性下标（-1 结束）、属性名下标、值的字符串偏移 |
| 之后 | 字符串池 |

和判定相关的节点：

- `<judge value="12">`：JA 窗口。
- `<speed>` ×3：`open` = 3/6/9，`t0`/`t1`/`t2` = 120/100/80、150/120/90、150/130/110（含义未确认）。
- `<judcom>`：`top last success miss minor bad good jw50 jw10 jw0 mt`，是评委台词的分类标签，不是判定参数。

## 7. 与流传说法的对照

| 说法 | 代码里的情况 |
|---|---|
| 高 Tension 时 JA 判定更宽松 | **不成立**。窗口只来自数据表，没有代码修改它 |
| 振り切り时拿不到 JA 奖励 | 部分成立：基础值上限 100 会截掉 +10，但"振り切り"对应多少能力值没有核对 |
| 自己数拍子比看灯准 | 与第 5 节一致（推测） |
| BPM 慢的曲子容易 JA | 按毫秒算窗口确实更宽 |
