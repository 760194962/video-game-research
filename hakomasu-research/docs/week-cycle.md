# 周循环（行动选择与推进一周）调查

目标：评估把 360 版的周循环改得接近街机版，即一周内可以既做レッスン又做営業，但オーディション每周只能做一次。
本文只做调查和可行性评估，没有改存档，也没有在游戏里试过补丁。结论全部来自对 `default.xex` 的反编译和存档数据。标注"推测"的条目只看过代码或数据，没有验证。

## 0. 结论

- 周数只在 `System::EndOfWeek`（vtable `+0xE8`）里推进。调用它的只有三处：夜间事务所（OfficeNight）退出、休息（OffSchedule）退出，以及晨间特殊事件跳过一周。レッスン、営業、オーディション本身都不推进周数；它们的结束场景都会走到 OfficeNight，由 OfficeNight 统一推进。
- 原版代码里**已经有"课程结束后接营业"的路径**，只在教程周启用：课程场景的"下一场景"函数在 `unit+0x244` 为 -3 或 -2（教程状态）时返回 0x12（PromotionChooser），否则返回 0x17（OfficeNight）。
- 所以最小改法只需改 1 条指令：把默认分支的 `li r30,0x17` 改成 `li r30,0x12`。效果是每次レッスン结束后进入営業选择，然后走交流事件、夜间事务所，只推进一周。オーディション只能从晨间菜单进入，而且会占满一整周，所以"每周最多一次"不需要另加限制。
- **游戏运行时会加载 TU**（`default.xexp`，0.0.0.1 → 0.0.2.1），代码地址整体平移了。补丁要用 TU 后的地址：`0x82324300: 3BC00017 → 3BC00012`。不打 TU 时对应的地址是 `0x823216F8`。两版的这个函数逐条比对过，逻辑相同。
- 主要代价：选了レッスン就必须接営業，不能只做课程；另外周末统计（PEVA 计数）只按一种行动记账（见第 7 节）。如果要做到"两项都可选、顺序任意"，需要代码洞和每周状态标志，单纯改 `.patch.toml` 里几条指令做不到。

## 1. 环境与方法

- 基础镜像：用 `tools/xex_decrypt.py` 解出的 `default.xex`（0.0.0.1）。
- TU 镜像：Xenia 实际加载的是 `content/0000000000000000/4E4D07DB/000B0000/TU_174Q1UR_0000004000000.00000000000G1/default.xexp`。日志里有 `XEX patch applied successfully: base version: 0.0.0.1, new version: 0.0.2.1` 和 `Module Hash: 2DE0C2DE0637583C`。xexp 的数据密钥要先把头部的 LZX 增量还原才能拿到，所以没有自己实现，而是用本机已有的 `xextool.exe`（iso2god 目录，XexTool v6.3）：`xextool -p tu.xexp -o patched.xex base.xex`，再用 `xextool -b patched.pe patched.xex` 导出镜像。入口点从 `0x823BA820` 变成了 `0x823BDED0`。
- 两版函数的对应：按 `mfspr r12,LR` 切出函数，把指令归一化（去掉分支偏移和 lis/addi/load/store 的立即数，只保留操作码和寄存器字段）后算哈希。下表里的函数在两版之间都是一一对应、内容相同的。
- Ghidra 设置与 `docs/audition.md` 第 6 节相同。另外在 `C:\Users\76019\tools\gscripts` 下新增了三个脚本：`FixThunks.java`（把 0x82451E00–0x82452000 的寄存器保存 thunk 设成可返回，并补反汇编每个调用之后的指令），`DecompList.java`（批量反编译），`DecompFix.java`（清掉一段范围后重建函数再反编译，用来处理被 thunk 截断的函数）。
- vtable 是按 MSVC RTTI 找的：TypeDescriptor（类名字符串 -8）→ CompleteObjectLocator（+0xC 指向 TypeDescriptor）→ vtable（COL 指针的下一个字）。

## 3. 数据结构

### UNIT（运行时对象，0x848 字节）

| 偏移 | 含义 | 依据 |
|---|---|---|
| +0x24 | 内嵌 `UNIT_TAG`（vt `+0x08` 返回它） | |
| +0x23C | 日历周，0~50 循环 | vt `+0x38`：不在特殊状态时 `+1`，到 0x33 归 0；`0x822490F0` 按它换算月份和周的显示 |

| +0x32C | 当前流行（推测） | `StartOfWeek` 每周写入 |

"推进一周"（vt `+0x14`，基础版 0x82248E38）：

```c
if (!this->isTutorial())            // vt+0x30：+0x244 < 0
    this->week = clamp(this->week + 1, 0, 0x34);
```

### 存档里的对应位置

UNIT 的反序列化函数 `0x8224A580` 依次读入 UNIT TAG、REPO、PEVA、6 元素数组、SONG，再读一个 14 个 int 的结构，然后是 0xC 字节和 0x10 字节（最后游玩时间）。按 Unit 槽布局，这个结构在槽内 `+0xAB0`：

| 槽内偏移 | 对应 UNIT 字段 |
|---|---|
| +0xAD8 | +0x23C 日历周 |
| +0xADC | +0x240 已过周数 |
| +0xAE0 | +0x244 教程状态 |

用现有存档核对过：同一个 Unit 的两份存档，已过周数 3→6，日历周 16→19，增量一致；成就存档的三个 Unit 是 49、38、50 周，都不超过 52。这个对应是从代码推出来的，没有改值后进游戏验证过（推测）。

`gamedata-format.md` 里 Unit 槽 `+0x350` 起的 14 个 int 是 `UNIT_TAG` 的数据：[0] 偶像人数，[1] 等级（0=S … 7），[2] 粉丝数，其余字段没有逐个解出。

`EndOfWeek` 按行动类型对 Unit PEVA 和制作人 PEVA 同时计数：

- 课程（0）：vt `+0xCC` 记第 1 次课程，`+0x48` 不为 0 时再用 `+0xD0` 记第 2 次。记录函数 0x82239120 按课程类型（+0x18 或 +0x20）给下标 3~8 加分，按评价（+0x1C 或 +0x24）给下标 15~18 加 1。
- 营业（1）：下标 9（+0x44）加 1，再按 +0x1C（0~3）给下标 11~14 之一加 1。

另外，`System+0xFC`（0x8223C2C0）按等级给粉丝数设下限：S 150 万，A 100 万，B 70 万，C 30 万，D 10 万，E 1 万，F/G 为 1。

## 4. 场景系统

每个 Produce 场景是一个外壳类加一个匿名命名空间里的 `Impl`。场景工厂 0x82293388 按固定顺序创建全部场景，再用 0x821F1830 依次注册到场景管理器，**场景 ID 就是注册顺序的下标**。每个场景 `Impl` vtable 的 `+0x4C` 是"下一场景 ID"函数（常量或按状态计算）；场景也可以用 vt `+0x54`（写 `+0x24`）临时指定下一场景。

只列和周循环有关的（创建函数用来核对类名，地址为基础版）：

|---|---|---|---|

| 8 | AuditionChooser | 0x8226BD28 | 9 |

OfficeMorning 菜单（0x822A8DF0）在栈上建一张表，按选项下标（场景 `+0x2C`）取下一场景：1→0x12 営業，2→0x15 レッスン，3→8 オーディション，4→0x13 休息。制作结束（`+0x31C`）时进入 0x1D（结局演唱会相关，推测）；特殊事件周（`+0x320`）直接进入 0x18 存档。

没有任何其他场景会把下一场景设成 8，所以试镜只能从晨间菜单进入。

## 5. 一周的流程

```
OfficeMorning 初始化 ── System::StartOfWeek
   │ 菜单
   ├─ 営業   → 0x12 PromotionChooser → 0x14 交流事件 → 0x17 OfficeNight
   ├─ レッスン → 0x15 LessonChooser → 0x27 课程 ─┬─ 教程(-3/-2) → 0x12 営業 → …
   │                                             ├─ +0x78==1   → 0x15 第二次课程
   │                                             └─ 其他        → 0x17 OfficeNight
   ├─ オーディション → 8 → 9 → 0xA → 0xB 结果 → (0xE 电视节目…) → 0x17 OfficeNight
   └─ 休息   → 0x13 OffSchedule ── 退出时 System::EndOfWeek → 0x18
0x17 OfficeNight ── 退出时 System::EndOfWeek → 0x18 OfficeNightSave（存档）→ 6
```

课程的"下一场景"函数（基础版 0x82321680，TU 版 0x82324288）：

```c
TODAY t = unit->getToday();
if (scene->tutorialState == -3 || scene->tutorialState == -2) {  // +0x2E8，来自 unit+0x244
    t.secondLesson = 0;  next = 0x12;      // 教程：课程后接营业
} else if (scene->bonusLesson == 1) {      // +0x78，由课程表按类型和评价决定
    t.secondLesson = 1;  next = 0x15;      // 再选一次课程
} else {
    t.secondLesson = 0;  next = 0x17;      // 进入夜间
}
unit->setToday(t);
return next;
```

`+0x2E8` 是课程场景初始化（0x8232C7B8）时从 `unit` vt `+0x2C`（即 `+0x244`）取的。`+0x244` 由 SetupUnit（0x822C4D80）在制作人还没有完成过 Unit 时设成 -3，所以这就是教程周。

## 6. 推进一周的路径

三条路径都汇到 `System::EndOfWeek`：

1. OfficeNight 退出（0x822ADD68）：普通的レッスン、営業、オーディション周。
2. OffSchedule 退出（0x822951D8）：休息周，经 vt `+0xD0` 转到 `+0xE8`。
3. `System+0xCC`（0x8223BA50）：OfficeMorning 退出时 `+0x320 == 1`（特殊事件周）调用，处理完直接 `this->EndOfWeek()`。

`EndOfWeek` 的结尾部分：

```c
if (!unit->isTutorial()) {        // +0x244 >= 0
    unit->advanceWeek();          // vt+0x14：+0x240 加 1，夹在 0~52
    unit->advanceCalendar();      // vt+0x38：+0x23C 加 1，51 周循环
} else {
    // -3 / -2 时先调用 System vt+0x70(1 或 2)
    unit->advanceTutorial();      // vt+0x28：-3→-2→-1→0
}
```

所以教程的几天不消耗周数。

## 7. 周结算会处理什么

`EndOfWeek`（0x82240CC0）按顺序：

1. 复制 Unit PEVA、制作人 PEVA、一个与回忆相关的对象（推测，Unit vt `+0x9C`）和 TODAY。
2. 记下本周开始时是否已到 52 周（Unit vt `+0x20`）。
3. 按 TODAY `+0x44` 和回忆对象的状态修正 `+0x44`，再按行动类型给 PEVA 计数（第 3 节）。
4. 行动类型为 2、7、8（休息）时，对每位偶像做一次处理（参数 7）。
5. 按 `+0x44` 调用 Unit 的 `+0xFC`、`+0xC0`、`+0xDC`、`+0xD4` 等（推测与回忆有关）。
6. TODAY `+0x2C` 为 0x60~0x63 时给制作人 PEVA[19] 置位（推测与营业有关）。
7. 若偶像状态为 9，进入特殊分支并按条件写偶像状态（推测与结局或引退有关）。
8. 粉丝差值：用 TODAY `+0x58`（开始时的粉丝基准）算出本周增量，加到两份 PEVA 的下标 10。这一项覆盖一周内所有活动，与做了几次行动无关。
9. 推进周或推进教程状态（第 6 节）。
10. 对 Unit 的 3 位偶像调用 `+0xE0(i, 值)`（每周的偶像状态更新，推测）。
11. 写回 PEVA 和回忆对象。
12. 若开始时已到 52 周，做制作结束处理：从列表移除 Unit 并整理存档槽。

`StartOfWeek`（0x8223CDB8）：重置 TODAY，记录粉丝基准，更新制作人每周数据，第 0 周时初始化 UNIT_TAG，刷新流行（Unit vt `+0xB4`），并在已过周数小于 0x31 时检查偶像状态 0xB、0xC（推测与引退相关）。

## 8. 改法草案

### 方案 A：课程后接营业（推荐，单条指令）

把课程"下一场景"函数的默认分支从 0x17 改成 0x12：

| 版本 | 地址 | 原值 | 新值 |
|---|---|---|---|
| TU 0.0.2.1（Xenia 实际加载的） | 0x82324300 | `3BC00017` `li r30,0x17` | `3BC00012` `li r30,0x12` |
| 基础版 0.0.0.1 | 0x823216F8 | 同上 | 同上 |

两个地址的原值都在镜像里核对过。

改后的流程：

- 选レッスン：课程 →（若有奖励课程则再上一次）→ 営業选择 → 交流事件 → 夜间事务所 → 推进 1 周。
- 选営業：不变。
- 选オーディション：不变，一周一次。
- 休息：不变。
- 教程：不变（走的是另一个分支）。

周数推进次数没有变化：仍然是每次 OfficeNight 或 OffSchedule 退出时推进一次。52 周期限、日历、等级和粉丝下限都按周计算，不受影响。周中状态不写进存档（只在 0x18 OfficeNightSave 存档，TODAY 也不在 UNIT 的序列化内容里），所以不会产生新的存档格式问题。

### 方案 B：课程和营业不推进周（不推荐）

在 `EndOfWeek` 里调用推进一周的位置（TU 0x82242CA8）加条件，行动类型为 0 或 1 时跳过。问题在于：

- 每次行动后仍然会经过夜间、存档和下一个早晨，`StartOfWeek` 会重新刷新流行、重置 TODAY、重新记录粉丝基准。时间不前进，但"每周"的事件照常发生，等于可以无限次行动，破坏 52 周的节奏。
- 需要读取 TODAY 并分支，一条指令改不出来，要用代码洞。

### 方案 C：同一周内课程、营业各一次，顺序任意（需要代码洞，目前不可行）

大致需要：

1. 一个每周清零的状态字（已上课、已营业），放在不会被存档、也不会被其他代码使用的内存里。TODAY 的字段都有用途，暂时没找到安全的空位。
2. 课程和营业的"下一场景"改成：另一项还没做 → 返回 6（OfficeMorning），否则 → 原来的下一场景。
3. OfficeMorning 初始化（0x822A32B0）调用 `StartOfWeek` 的地方加条件，周中返回时跳过。
4. OfficeMorning 菜单禁用本周已做的项目和试镜。菜单的可用性标志（推测在场景 `+0x5A8` 起的 16 个 int）没有分析。
5. 晨间脚本和对话默认每次进入都是新的一周，重复进入时的表现未知。

`.patch.toml` 可以用 `array` 把代码写进 `.text` 里函数之间的空白处作为代码洞（推测可行，没有验证 Xenia 在哪个阶段应用补丁）。这一方案改动多、未知多，建议先在游戏里验证方案 A 再考虑。

## 9. 风险（方案 A）

1. **不能只上课了。** 课程后必定进入営業选择。PromotionChooser 的"下一场景"只会返回 0x14 或 0x19，没有看到返回早晨或夜间的取消路径。能不能按 B 退出，需要在游戏里确认。
2. **周结算只按一种行动记账。** 行动类型（TODAY `+0x10`）和第 1 次结果（`+0x1C`）都是单一字段：
   - 如果営業把行动类型写成 1，那么这一周 PEVA 只记营业，课程的类型和评价计数（下标 3~8、15~18）丢失；
   - 如果営業不写，那么只记课程，营业计数（下标 9、11~14）丢失；
   - 营业很可能会把自己的结果写进 `+0x1C`，覆盖课程评价，导致按课程记账时评价错位。
   
   能力值是在课程和营业场景里直接加的，不在 `EndOfWeek` 里（推测），所以影响的应该主要是统计、成就计数（A100/C100/L100/M100 相关下标）和制作人评价。
3. **界面和对话。** daytimer 和夜间对话按行动类型选内容。教程本来就走这条路径，说明场景能衔接，但非教程周的对话和演出是否自然，没有验证。
4. **平衡性。** 每个课程周多一次营业和交流事件，成长和粉丝增长会明显加快；52 周期限不变，等于行动次数增加。
5. **奖励课程。** `+0x78 == 1` 时仍然先上第二次课程，再接营业，流程会更长。第二次课程结束时同样走默认分支（`+0x48` 置 0），这与原版相同。
6. **TU 与 hash。** 补丁地址只对 TU 0.0.2.1 有效。换 TU 或不装 TU 时必须换地址和 hash，否则会改到别的指令。
